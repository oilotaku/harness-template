# 任務拆解與目標設定方法

## 1. 拆解原則

- **依「可獨立驗收」拆分**，而不是依「檔案」或「函式」拆分。
  一個 task 的驗收標準應該可以獨立於其他 task 判斷通過與否。
- **每個 task 只對應一個 layer**（例如：資料層、API 層、UI 層），
  避免一個 task 同時要求後端與前端變更，導致實作者/檢驗者職責混淆。
- **依賴關係要明寫**：若 task B 依賴 task A 的輸出（例如 API 合約），
  在 task-spec 的 `depends_on` 欄位標明，Orchestrator 依此排派工順序，
  不可讓沒有依賴關係的任務被迫序列化，浪費平行化機會。

## 2. 目標設定（每個 task 都要回答）

1. **這個 task 完成後，使用者/系統能多做到什麼事？**（一句話目標）
2. **驗收標準是什麼？**（可被檢驗者寫成測試的具體條件，避免用「效能要好」
   這種無法直接驗證的敘述，要換成「95 百分位延遲 < 200ms」這種可測量的形式）
3. **明確的範圍邊界**：哪些檔案/模組會被改動，哪些絕對不能動。
4. **禁止事項**：這個 task **不應該**做什麼（防止實作者過度發揮）。

## 3. 拆解流程

```
需求
 │
 ├─ 先問：這個需求有沒有清楚到可以拆 task？(沒有 → 先發問)
 ├─ 找出可獨立驗收的邏輯單元
 ├─ 每個單元寫一份 task-spec（見 templates/task-spec-template.md）
 ├─ 標出彼此的 depends_on 關係
 └─ 依 docs/model-thinking-matrix.md 標註模型/思考層級
```

## 4. blocked 任務的處理原則

implementer 依 `implementer-generic.md` 的停損規則回報 `blocked` 時
（同一條驗收標準連續失敗 ≥3 次，或需要修改範圍外的檔案），
**不可以把該 task 原樣重派給同一個或另一個 implementer session 重試**，
必須先由 Orchestrator 判斷根因——通常是 task-spec 本身描述不清、
驗收標準與實際情況矛盾，或拆分粒度有問題——修正 task-spec
（或視情況重新指派 verifier-test-writer 修正測試）之後才能重新派工。
原樣重派等於把「規格不清楚」的問題丟給 implementer 自己猜，
違反黃金法則第 7 條。

## 5. 什麼時候不該拆更細

如果拆到「一個 task 小到沒有獨立驗收意義」（例如把一個函式的三行邏輯拆成三個
task），就是拆過頭了。經驗法則：一個 task 的實作時間如果讓一個具備該語言能力
的工程師來做，大約落在「幾十分鐘到半天」之間，太小或太大都應該重新切分。
