# 根因分析與修正流程（RCA → Fix）

驗收不通過、測試變紅、CI 掛掉、防護機制誤擋或漏擋——這些狀況本身不是問題，
**用錯方法處理它們才是**。這份文件定義的是「出事之後照著走的步驟」，
避免流程退化成「一路試到綠燈為止」。

適用時機（任何一項成立就走這套）：

- `verifier-reviewer` 判定不通過
- 公開/隱藏測試失敗，或 `verify-locks.py` 回報竄改
- CI 在任一平台/版本紅燈
- 防護機制行為不如預期（該擋的沒擋、不該擋的擋了）
- implementer 觸發停損規則（同一條驗收標準連續失敗 ≥3 次）

---

## 0. 三條核心原則

1. **症狀不是根因。** 「測試紅了」是症狀；「這個函式在 Windows 上用系統
   ANSI 代碼頁編碼中文」才是根因。修症狀會讓同一個 bug 換個形狀再回來。
2. **先問「為什麼這個沒被更早抓到」。** 每個 bug 其實是兩個缺陷：程式碼錯了，
   而且**沒有任何一道防線發現它**。只修前者，下一個同類 bug 一樣是無聲的。
3. **沉默失效優先於吵鬧失效。** 會噴錯的問題自己會找上你；
   「看起來正常但其實沒作用」的問題（fail-open、零測試假通過、鎖定形同虛設）
   才是這個模板真正的敵人——它們可以存在好幾個月都沒人發現。

---

## 1. 步驟

### 步驟 1：凍結證據，先不要動手改

- 記下**完整**的錯誤輸出、exit code、平台/版本、觸發的指令。
- 記下當時的 commit sha。
- **不要**在還沒搞清楚之前就開始改程式碼——改了之後就重現不出來了。

> 這一步的產出直接寫進 `.harness/progress/<task_id>.md`
> （見 `token-strategy.md` §3.2）。被打斷之後，這幾行就是你不用重查一次的理由。

### 步驟 2：穩定重現

在**能重現**之前，任何修正都只是猜測。

- 找出最小的重現指令（單一測試案例 > 整組測試 > 整個 CI job）。
- 確認它**每次都失敗**。若時有時無，先處理不確定性本身：
  跟順序有關？跟時間/亂數有關？跟殘留狀態有關？
- **重現不了就不要往下走**，回報 Orchestrator，不要假裝已經修好。

> 「重跑一次就過了」不是結論，是待查事項。詳見下面「禁止事項」。

### 步驟 3：定位——縮小到一行

用刪去法，不要用直覺：

- 二分：把重現情境一半一半砍掉，看失敗跟著哪一半走。
- 對照：換平台、換版本、換 locale、換路徑寫法，找出**唯一的差異變數**。
- 讀實際值：把中間結果印出來對照期望值，不要靠推理臆測。

定位完成的標準是**你可以指出一行程式碼，並說明它在什麼條件下做錯什麼**。
說不出這句話就還沒定位完。

### 步驟 4：往上追一層——為什麼防線沒攔到

這一步最常被跳過，也最重要。針對已定位的根因，逐一問：

| 問題 | 若答案是「沒有」 |
|---|---|
| 有測試涵蓋這個情境嗎？ | 補測試（步驟 5 會先讓它變紅） |
| CI 跑得到這個情境嗎？ | 補矩陣維度（平台／版本／locale／設定檔有無） |
| 失效時會有訊號嗎？ | 這是**沉默失效**，優先修：改成 fail-closed 或加自我檢查 |
| 同一類寫法在別處還有嗎？ | 走步驟 6 |

### 步驟 5：先讓測試變紅，再修

順序不可顛倒：

1. 寫一個**會失敗**的測試案例，重現這個 bug（斷言「正確行為」，不是「目前行為」）。
2. 執行它，**確認它真的紅**。沒紅過的測試不算測試——它可能根本沒跑到，
   或斷言寫得永遠成立。
3. 修正程式碼。
4. 再跑一次，確認它綠了，而且**其餘所有測試仍然綠**。

修正本身要**最小**：只處理已定位的根因，不順手重構、不擴大範圍
（黃金法則第 4 條）。想順手改的東西記下來，交給 Orchestrator 開新 task。

### 步驟 6：找同類（class of bug）

一個 bug 很少只出現一次。修完之後搜尋整個 repo：**同樣的寫法還有幾處？**

如果同類散佈很廣，比起逐一修正，優先考慮**結構性的解法**——
讓這一類錯誤下次寫出來就會被擋下：靜態檢查、共用函式、型別、CI 的新維度。

> 本 repo 的實例：「檔案讀寫沒指定編碼」修掉之後，加了一個 AST 靜態檢查案例
> 掃描所有腳本，再加一個 `LC_ALL=C` 的 CI 步驟。從此這一類 bug 寫出來就會紅。

### 步驟 7：驗證與記錄

- 本機跑完整回歸測試（README 有完整指令），不是只跑改到的那組。
- 推上去確認 CI 在**所有**平台/版本上都綠。
- 更新 `.harness/progress/<task_id>.md`。
- 若這個根因反映的是流程或規格層級的問題（不是單純寫錯），
  由 **Orchestrator** 依 `memory-management.md` §3 判斷要不要寫進記憶。

## 2. 角色分工

出事的當下最容易發生的事，就是角色界線糊掉。

| 角色 | 可以做 | 不可以做 |
|---|---|---|
| **implementer** | 步驟 1–3、5（在 task-spec 範圍內修正）、6 的搜尋 | 改公開測試、改驗收標準、擴大修改範圍、自行判定「這不算 bug」 |
| **verifier-reviewer** | 判定通過/不通過、指出根因、要求補測試 | 動手改實作程式碼（改了就變成自己驗自己） |
| **verifier-test-writer** | 補測試案例、重新鎖定、必要時重寫並重新封存隱藏測試 | 把隱藏測試內容洩漏給 implementer |
| **Orchestrator** | 決定是否修 task-spec、是否重新派工、是否開新 task、寫記憶 | 自己下去改程式碼或改測試 |

**公開測試改了就要重跑 `lock-tests.py`**，否則 `verify-locks.py` 會把合法修正
判定成竄改；而這個動作只能由 verifier 做。

## 3. 禁止事項

以下每一項都能讓燈變綠，而且每一項都是**把問題藏起來**：

- 禁止跳過、停用、或標記忽略任何測試來讓它變綠。
- 禁止放寬斷言（把期望值改成目前的錯誤輸出）。
- 禁止把 `try/except` 加寬到吞掉例外，只為了不要中斷。
- 禁止把失敗歸因為「flake」而不查——除非有證據：
  同一個 commit 之前綠過、失敗發生在測試本體執行之前（checkout/安裝/runner）、
  或錯誤指向的服務跟這次改動完全無關。**沒有證據就是真的失敗。**
- 禁止在防護機制上「先放行、之後再說」——那正是 fail-open，
  這個 repo 已經為它付過一次代價。
- 禁止趁修 bug 順手重構不相關程式碼（黃金法則第 4 條）。

## 4. 這個 repo 踩過的真實案例

拿來對照上面的步驟，比抽象原則好記：

| 症狀 | 根因 | 防線缺口（步驟 4） | 結構性修正（步驟 6） |
|---|---|---|---|
| guard 在設定檔壞掉時「放行」 | 模組層的 import/載入例外落在 `try` 之外 → exit 1 = 允許 | 沒有任何測試驗證「壞設定要 fail-closed」 | 啟動錯誤集中成 `_STARTUP_ERROR`，`main()` 一開始就 `_block()` |
| 隱藏測試「全部通過」但其實一個都沒跑 | `unittest discover` 不遞迴進沒有 `__init__.py` 的子目錄，Ran 0 tests + exit 0 | 沒有人檢查「跑了幾個測試」 | runner 偵測零測試輸出並判定不通過 |
| 所有腳本在 Windows 一印中文就崩潰 | 主控台用系統 ANSI 代碼頁 | CI 只跑 Linux | 加 Windows/macOS 矩陣 + 啟動時 reconfigure stdout/stderr |
| 檔案讀寫在非 UTF-8 locale 下亂碼 | `open`/`read_text` 依系統預設編碼 | 同上，Linux 預設 UTF-8 蓋住了問題 | AST 靜態檢查 + `LC_ALL=C` 的 CI 步驟 |
| 第一版 guard 有多個繞過寫法 | 用「指令字串是否含子字串」比對 | 完全沒有回歸測試 | 改成解析 + 路徑正規化，並補 59 個案例 |

共同點：**五個裡面有四個是沉默的**。這就是原則 3 的由來。

## 5. Token 與中斷（訂閱制方案）

除錯是最容易失控的 token 消耗：一路試、一路重跑、一路重讀。
`token-strategy.md` §3 的那幾條在這裡格外適用：

- **步驟 1 的證據與步驟 3 的結論寫進 `.harness/progress/`**，
  撞到用量上限之後恢復就不用重查一次。
- **一次只查一件事。** 同時改三個地方再跑，紅了你也不知道是誰造成的，
  等於白花一輪。
- **先小後大**：重現與二分是機械工作，抓根因才需要重量模型。
