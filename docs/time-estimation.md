# 執行時間預測

Orchestrator 拆解任務時必須決定「這輪做幾個」「要不要分批」「值不值得現在開」。
在此之前那個決定完全憑感覺，而憑感覺的估時有兩個典型的失效方式：

1. **用「一切順利」當基準**——但 CI 來回、規格澄清、失敗重試都是常態，不是意外。
2. **估完就丟掉**——沒有人回頭對照實際值，所以永遠不會變準。

這份文件定義的方法很簡單：**先分類，再用單價表估區間，最後用這個專案自己的歷史校準。**
落地在 `scripts/timing.py`（純函式）與 `scripts/estimate-time.py`（指令入口）。

---

## 1. 三條原則

1. **一律給區間，不給單一數字。** 單一數字會被當成承諾，而估時不是承諾。
2. **無界的題目不估。** 「把所有繞過寫法都擋掉」這種沒有終點的題目，
   給不出估時不是因為估不準，是因為**題目還沒被界定**。
   `estimate()` 對這類任務丟 `UnboundedTask` 而不是回一個數字——
   跟 `service-scan.py` 在掃描不完整時不給建議連接埠區間是同一條原則。
3. **估時要跟「什麼時候拿得到結果」分開。** 前者是 agent 的工作時間，
   後者還包含人審等待與撞到用量上限的等待，那兩件事不在模板控制範圍內。

---

## 2. 成本公式

```
總時間 = Σ(每個任務的分類單價)
       + PR 週期數 × 週期固定開銷
       + PR 週期數 × CI 紅燈機率 × 重試成本
       再乘上這個專案的校準係數
```

### 分類單價（本 repo 實測，單位：分鐘）

| 分類 | 說明 | 單價 |
|---|---|---|
| `doc` | 純文件／規則調整，不動程式碼 | 5–10 |
| `wiring` | 改幾個既有檔案的接線，附帶 0–2 個測試 | 10–15 |
| `module` | 新模組 + 專屬測試套件 + CI 接線 | 15–25 |
| `structural` | 結構性改動：新機制、跨多檔、預期會有來回 | 40–90 |
| `unbounded` | 沒有明確終點的題目 | **不可估** |

其他常數：PR 週期固定開銷 3–5 分（push、等 CI、寫 PR 描述）；
CI 紅一輪 5–15 分；預設 CI 紅燈機率 0.3。

### 這些數字是怎麼來的

不是猜的，是這個 repo 自己的三個資料點：

| 實際做過的 | 內容量 | 實際耗時 |
|---|---|---|
| RCA 流程（PR #4） | 純文件 + 4 處接線 | 約 7 分 |
| P3-2（PR #5） | 2 個新模組 + 32 個測試 + CI + 6 處文件 | 約 15 分 |
| 第一批（PR #2） | 8 個項目 + CI + 126 個測試 + 兩輪 Windows 編碼修正 | 1 小時以上 |

**換一個專案，這些單價就不該直接沿用**——所以下面的校準機制才是重點。

---

## 3. 用法

```bash
# 估一批任務：3 個純文件 + 1 個新模組，分 2 個 PR 週期送出
python3 scripts/estimate-time.py --tasks doc:3,module:1 --rounds 2

# 給 Orchestrator 讀（stdout 只有 JSON）
python3 scripts/estimate-time.py --tasks doc:3,module:1 --rounds 2 --json

# 任務做完之後回填實際值
python3 scripts/estimate-time.py --record T-012 --estimated 20 --actual 34
```

估時結果寫進 task-spec 的「預估耗時」欄位；實際值在驗收後回填。

---

## 4. 校準：估時只有被對照過才會變準

校準係數 = `median(實際 / 估計)`，存在 `.harness/timing.json`（不進版控）。

刻意的保守設計：

- **樣本少於 3 筆時不套用校準（係數固定為 1.0）。**
  用一兩筆樣本調係數只是把雜訊放大成偏見，而且會讓人以為估時「有根據」——
  那比明講「還沒校準」更糟。
- **用中位數，不用平均。** 一次爆掉的任務（例如踩到跨平台編碼問題）
  不該把之後所有估時都拉高一倍。
- **壞掉的紀錄直接略過**（缺欄位、型別錯、除以零），不讓一筆髒資料炸掉整組校準。
- 紀錄檔不存在或壞掉時回空清單——校準是加分項，不是必要條件。

沒有回填實際值的話，係數永遠是 1.0，等於一直用**別的專案的單價**在估自己的專案。
所以回填不是行政流程，是這套方法唯一會變準的環節。

---

## 5. 不含在估時裡的兩件事

| 不含 | 為什麼 |
|---|---|
| 人審與合併決策的等待 | 不在模板控制範圍；要講「什麼時候拿得到」要另外加 |
| 撞到用量上限之後的等待與恢復 | 見 `token-strategy.md` §3.1——那是複利成本，不是線性延長 |

第二項在訂閱制方案下特別重要：**agent 的工作時間不變，但牆上時間可能翻倍以上**。
如果要報一個「什麼時候會好」，這兩項要另外估，不要混進上面的數字裡。

---

## 6. 禁止事項

- 禁止把估時當成承諾或截止時間。它是拆解時的決策依據，不是對使用者的保證。
- 禁止對無界任務硬給數字。先把題目界定成有界範圍（例如「只處理列舉出來的 N 種情況」），
  再回來估。
- 禁止只報樂觀端。要報就報區間；只講 low 等於預設一切順利。
- 禁止為了讓估時好看而縮小範圍卻不說。範圍變了就要重估，並寫明變了什麼。
- 禁止用平行度去壓縮估時。平行縮短的是牆上時間，不是工作量，
  而且在訂閱制方案下會等倍放大撞到上限的機率（`token-strategy.md` §3.4）。

---

## 7. 檢查清單

拆解完、派工前：

- [ ] 每個 task 都有分類嗎？有沒有分類不出來的（那就是 `unbounded`，要先界定）？
- [ ] 估時寫進 task-spec 了嗎？
- [ ] 這輪打算分幾個 PR 週期？（週期越多，固定開銷越高——這是分批的成本）
- [ ] 要不要跟使用者說明「不含人審等待與用量上限等待」？

驗收完：

- [ ] 實際耗時回填了嗎？（`--record`；不回填就永遠不會變準）
