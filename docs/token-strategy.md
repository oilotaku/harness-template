# Token 成本策略

本模板的架構**天生吃 token**：一個 task 至少要開 3 個不共用上下文的子智能體
session，而且預設幾乎全用重量模型。這不是設計缺陷——「獨立驗證鏈」的價值正是
建立在「不共用上下文」上（見 `implementer-verifier-workflow.md`）。

但「必要的成本」跟「浪費」是兩回事。這份文件先把錢花在哪裡量出來，
再依 CP 值排出該省哪些、以及**哪些絕對不該省**。

---

## 1. 成本公式：大小 × 載入次數

直覺會想「先精簡最大的檔案」，那是錯的優先順序。真正的成本是：

```
總成本 = 檔案大小 × 這個檔案被載入幾次
```

而 `.claude/agents/` 底下的每個子智能體都是**獨立 session**，
每個 session 都要重新載入 `CLAUDE.md` 與自己的定義檔。
所以 `CLAUDE.md` 的乘數是「agent 數 × task 數」，是全 repo 最高的。

### 實測（2026-09-10，字元數）

| 檔案 | 大小 | 每個 task 載入幾次 |
|---|---|---|
| `CLAUDE.md` | 6,427 | **每個 session 各一次**（≥3） |
| `verifier-test-writer.md` | 6,137 | 1 |
| `verifier-reviewer.md` | 5,498 | 1 |
| `orchestrator.md` | 5,133 | 1（每輪任務一次） |
| `implementer-generic.md` | 2,409 | 1 |
| 三支掃描腳本的輸出合計 | 1,384 | 每個 task 一次（若不快取） |

一個 task 光是「還沒開始做事」的固定載入：

```
test-writer   6,427 + 6,137 = 12,564
implementer   6,427 + 2,409 =  8,836
reviewer      6,427 + 5,498 = 11,925
                      合計   ≈ 33,325 字元
```

再加上 Orchestrator 自己（`CLAUDE.md` + `orchestrator.md` + 掃描輸出
+ 拆解／模型／記憶三份 docs）≈ 23,000 字元。

**一個 task 的固定開銷大約是 5.6 萬字元**（粗估 3～5 萬 token，
實際依 tokenizer 而異），而這還沒包含 task-spec、程式碼、測試輸出。
十個 task 的專案，光固定開銷就是幾十萬 token。

> ⚠️ `docs/improvement-suggestions.md` 是 39,142 字元——**比其他所有 docs 加起來還大**。
> 它是一份歷史審視報告，只給人看，**絕對不要出現在任何子智能體的閱讀路徑上**。
> 不小心讓一個 agent 讀它，等於一次燒掉一個 task 的固定開銷。

## 2. 依 CP 值排序的節省措施

### 2.1 把 task-spec 寫自足（最高 CP 值）

固定開銷至少是可預測的；**真正不可控的是「implementer 為了搞懂需求而到處搜尋程式碼」**。
一次漫無目的的 `Grep` + 讀五個檔案，可能就超過整個固定開銷。

所以「規格寫得好」不只是品質問題，直接就是 token 問題：

- task-spec 要寫清楚「可以改動哪些檔案」（`templates/task-spec-template.md`
  的「範圍邊界」欄位）——implementer 就不必自己找
- 已知的既有介面、資料結構、錯誤碼直接寫進 spec，不要讓實作者去翻
- 有歧義先問（黃金法則第 7 條）。**一次澄清問答遠比一輪失敗的實作便宜**

反過來說，`implementer-generic.md` 的停損規則（同一條驗收標準連續失敗 ≥3 次）
在 token 帳上是很貴的：三次失敗 = 三輪完整實作 + 三次測試執行。
規格不清楚時越早停損越省。

### 2.2 模型指派改成「先小後大」，而不是恆定最高

`model-thinking-matrix.md` 原本把幾乎所有檢驗者都定成恆定 opus/high。
但驗收其實是兩件性質不同的事：

| 驗收動作 | 需要的推理強度 |
|---|---|
| 跑測試、比對 exit code、對照驗收標準表 | 低——這是機械執行 |
| 抓作弊／取巧模式、判斷「這算不算範圍外變更」 | 高——需要懷疑視角 |

所以低風險（L1/L2）任務可以**先用中小模型跑第一輪驗收**，
只有在出現以下訊號時才升級到重量模型重驗：

- `verify-locks.py` 或 `run-hidden-tests.py` 回報異常
- 靜態審查發現任何可疑模式
- 實作變更超出 task-spec 宣告的範圍邊界
- task 標記 `security_review: true`

**但 L3/L4（跨模組、安全、金流、資料遷移）不適用這條**——
那些任務漏判一次的代價遠高於省下的 token。

### 2.3 掃描結果快取

黃金法則第 5 條要求「任何任務開始前」執行機器與服務掃描。
多 task 專案照字面執行會重複跑 N 次，每次輸出都進上下文。

同一個 session、同一台機器（`env-guard.py` 判定指紋相符）之內，
掃描結果可以重用一次，不必每個 task 重掃。**跨 session 或指紋不符時必須重掃**——
那正是這條法則要防的事。

（機器可讀的 `--json` 輸出讓 Orchestrator 不必解析中文散文，
是 `improvement-suggestions.md` 的 P3-2，尚未實作。）

### 2.4 `CLAUDE.md` 維持「索引」角色

它的乘數最高，所以它應該只寫**規則與指向**，細節放 `docs/`：
需要的 agent 才讀，不需要的就不用付這個成本。

現行的 §5 記憶管理就是這個寫法的範例——只留三行摘要 + 一個指向。
新增內容進 `CLAUDE.md` 之前先問：**這件事是不是每個 session 都必須知道？**
不是的話，寫進 `docs/` 並在該讀的地方指過去。

### 2.5 只把「必要範圍」交給子智能體

- implementer 只需要 task-spec + 公開測試 + 範圍邊界內的程式碼
- verifier-reviewer 需要的是**測試結果與變更**，不是整個 repo
- 失敗的測試輸出比全部通過的輸出有用得多；`run-hidden-tests.py`
  已經只在失敗時印出完整訊息

## 3. 絕對不該省的地方

省 token 很容易滑坡成「把防線拆掉」。以下幾項省下來的錢，
換來的是整套機制失去意義：

| 不該省 | 為什麼 |
|---|---|
| 檢驗者與實作者分開 session | 共用上下文就等於自己驗自己，整個 SE-CoVe 前提消失 |
| 隱藏測試機制 | 它就是這個模板的核心價值 |
| 需求釐清的問答 | 省一輪問答，通常換來三輪失敗實作，更貴也更慢 |
| L3/L4 任務的重量模型 | 漏判一次的代價遠高於模型差價 |
| 回歸測試（126 案例） | 機制退化是無聲的，測試是唯一訊號 |

### 一個常見誤解：平行度不省 token

`machine-profile.py` 決定的「同時可派出幾個子智能體」是**時間**的最佳化，
不是 token 的。三個 task 平行跑跟序列跑，總 token 一樣多——
平行只是讓你早點知道結果。真要省 token，要從上面第 2 節下手。

## 4. 檢查清單

開始一輪任務前：

- [ ] task-spec 的「範圍邊界」有沒有填？（不填 = implementer 自己去找 = 最貴）
- [ ] 有沒有歧義該先問？（黃金法則第 7 條）
- [ ] 這輪的掃描結果能不能重用上一輪的？（同 session + 指紋相符）
- [ ] 這個 task 真的需要 L3/L4 嗎，還是 L2 就夠？
- [ ] 有沒有把 `improvement-suggestions.md` 這類歷史文件放進 agent 的閱讀路徑？

改動 `CLAUDE.md` 前：

- [ ] 這件事是不是每個 session 都必須知道？不是就放 `docs/`。
