# Token 成本策略

本模板的架構**天生吃 token**：一個 task 至少要開 3 個不共用上下文的子智能體
session，而且預設幾乎全用重量模型。這不是設計缺陷——「獨立驗證鏈」的價值正是
建立在「不共用上下文」上（見 `implementer-verifier-workflow.md`）。

但「必要的成本」跟「浪費」是兩回事。這份文件先把錢花在哪裡量出來（§1），
再依 CP 值排出該省哪些（§2）、訂閱制方案下額外要注意的**消耗速率與可恢復性**（§3）、
以及**哪些絕對不該省**（§4）。

---

## 1. 成本公式：大小 × 載入次數

直覺會想「先精簡最大的檔案」，那是錯的優先順序。真正的成本是：

```
總成本 = 檔案大小 × 這個檔案被載入幾次
```

而 `.claude/agents/` 底下的每個子智能體都是**獨立 session**，
每個 session 都要重新載入 `CLAUDE.md` 與自己的定義檔。
所以 `CLAUDE.md` 的乘數是「agent 數 × task 數」，是全 repo 最高的。

### 實測（2026-09-10，字元數）

| 檔案 | 大小 | 每個 task 載入幾次 |
|---|---|---|
| `CLAUDE.md` | 6,427 | **每個 session 各一次**（≥3） |
| `verifier-test-writer.md` | 6,137 | 1 |
| `verifier-reviewer.md` | 5,498 | 1 |
| `orchestrator.md` | 5,133 | 1（每輪任務一次） |
| `implementer-generic.md` | 2,409 | 1 |
| 三支掃描腳本的輸出合計 | 1,384 | 每個 task 一次（若不快取） |

一個 task 光是「還沒開始做事」的固定載入：

```
test-writer   6,427 + 6,137 = 12,564
implementer   6,427 + 2,409 =  8,836
reviewer      6,427 + 5,498 = 11,925
                      合計   ≈ 33,325 字元
```

再加上 Orchestrator 自己（`CLAUDE.md` + `orchestrator.md` + 掃描輸出
+ 拆解／模型／記憶三份 docs）≈ 23,000 字元。

**一個 task 的固定開銷大約是 5.6 萬字元**（粗估 3～5 萬 token，
實際依 tokenizer 而異），而這還沒包含 task-spec、程式碼、測試輸出。
十個 task 的專案，光固定開銷就是幾十萬 token。

> ⚠️ `docs/improvement-suggestions.md` 是 39,142 字元——**比其他所有 docs 加起來還大**。
> 它是一份歷史審視報告，只給人看，**絕對不要出現在任何子智能體的閱讀路徑上**。
> 不小心讓一個 agent 讀它，等於一次燒掉一個 task 的固定開銷。

## 2. 依 CP 值排序的節省措施

### 2.1 把 task-spec 寫自足（最高 CP 值）

固定開銷至少是可預測的；**真正不可控的是「implementer 為了搞懂需求而到處搜尋程式碼」**。
一次漫無目的的 `Grep` + 讀五個檔案，可能就超過整個固定開銷。

所以「規格寫得好」不只是品質問題，直接就是 token 問題：

- task-spec 要寫清楚「可以改動哪些檔案」（`templates/task-spec-template.md`
  的「範圍邊界」欄位）——implementer 就不必自己找
- 已知的既有介面、資料結構、錯誤碼直接寫進 spec，不要讓實作者去翻
- 有歧義先問（黃金法則第 7 條）。**一次澄清問答遠比一輪失敗的實作便宜**

反過來說，`implementer-generic.md` 的停損規則（同一條驗收標準連續失敗 ≥3 次）
在 token 帳上是很貴的：三次失敗 = 三輪完整實作 + 三次測試執行。
規格不清楚時越早停損越省。

### 2.2 模型指派改成「先小後大」，而不是恆定最高

`model-thinking-matrix.md` 原本把幾乎所有檢驗者都定成恆定 opus/high。
但驗收其實是兩件性質不同的事：

| 驗收動作 | 需要的推理強度 |
|---|---|
| 跑測試、比對 exit code、對照驗收標準表 | 低——這是機械執行 |
| 抓作弊／取巧模式、判斷「這算不算範圍外變更」 | 高——需要懷疑視角 |

所以低風險（L1/L2）任務可以**先用中小模型跑第一輪驗收**，
只有在出現以下訊號時才升級到重量模型重驗：

- `verify-locks.py` 或 `run-hidden-tests.py` 回報異常
- 靜態審查發現任何可疑模式
- 實作變更超出 task-spec 宣告的範圍邊界
- task 標記 `security_review: true`

**但 L3/L4（跨模組、安全、金流、資料遷移）不適用這條**——
那些任務漏判一次的代價遠高於省下的 token。

### 2.3 掃描結果快取

黃金法則第 5 條要求「任何任務開始前」執行機器與服務掃描。
多 task 專案照字面執行會重複跑 N 次，每次輸出都進上下文。

同一個 session、同一台機器（`env-guard.py` 判定指紋相符）之內，
掃描結果可以重用一次，不必每個 task 重掃。**跨 session 或指紋不符時必須重掃**——
那正是這條法則要防的事。

三支掃描腳本都有 `--json`（stdout 只有 JSON），Orchestrator 直接讀欄位，
不必解析中文散文——同一段文字每次可能被解讀成不同數字，那既不穩定也更貴。
結果會留在 `.harness/last-scan.json`，能力指紋相同時可以重用。

### 2.4 `CLAUDE.md` 維持「索引」角色

它的乘數最高，所以它應該只寫**規則與指向**，細節放 `docs/`：
需要的 agent 才讀，不需要的就不用付這個成本。

現行的 §5 記憶管理就是這個寫法的範例——只留三行摘要 + 一個指向。
新增內容進 `CLAUDE.md` 之前先問：**這件事是不是每個 session 都必須知道？**
不是的話，寫進 `docs/` 並在該讀的地方指過去。

### 2.5 只把「必要範圍」交給子智能體

- implementer 只需要 task-spec + 公開測試 + 範圍邊界內的程式碼
- verifier-reviewer 需要的是**測試結果與變更**，不是整個 repo
- 失敗的測試輸出比全部通過的輸出有用得多；`run-hidden-tests.py`
  已經只在失敗時印出完整訊息

## 3. 訂閱制（Pro）下的真正限制：速率，不是總量

前面兩節談的是「總量」。但在 Claude Pro 這種**訂閱制**方案底下，
你付的錢是固定的，會咬人的不是花費，而是**用量上限**：
在一段滾動時間視窗內用掉太多，就會被擋住，必須等到視窗重置才能繼續。

這件事會把成本模型整個換掉：

| | 用量計費（API） | 訂閱制（Pro） |
|---|---|---|
| 稀缺的是什麼 | 錢 | **視窗內的額度** |
| 超支的後果 | 帳單變高 | **停下來等** |
| 該最佳化什麼 | 總 token 量 | **消耗速率 + 中斷後的恢復成本** |

> 本節不寫任何具體的額度數字或視窗長度——那些會隨方案調整，
> 寫死在文件裡只會過期誤導人。這裡談的是**機制**，不是數字。

### 3.1 撞上限的代價是複利的

撞到上限不是「損失等待的那段時間」而已，真正貴的是**恢復**：

```
撞上限 → 等待 → session 斷掉 → 重開
   → 重載 CLAUDE.md + agent 定義檔 + task-spec
   → 再花一輪 token 搞清楚「上次做到哪、為什麼這樣做」
   → 固定開銷又付一次（見 §1：約 5.6 萬字元）
   → 額度消耗得更快 → 更早撞到下一次上限
```

也就是說：**每撞一次上限，就多付一次固定開銷，而那次固定開銷又讓你更快撞牆。**
在 Pro 方案下，最該最佳化的其實不是「一個 task 花多少 token」，
而是「被打斷之後要花多少 token 才能回到原本的進度」。

### 3.2 可恢復性：進度要寫在檔案裡，不能只活在對話裡

上面那條複利之所以成立，是因為目前**任務進度只存在於對話上下文中**。
上下文一沒，就只能靠重讀整個 repo 重建。

解法很單純：**任何跨 session 需要知道的狀態，都要落地成檔案。**
這樣恢復的成本是「讀一個小檔案」，而不是「重建整段推理」。

模板裡已經有一部分是這樣做的（這也是它們當初被設計成檔案的原因之一）：

| 已落地 | 檔案 | 恢復時取代了什麼 |
|---|---|---|
| 任務規格 | `templates/task-spec-template.md` 產出的 spec | 重新問一次需求 |
| 公開測試鎖定 | `.harness/locked-tests.list` | 重新確認測試有沒有被動過 |
| 隱藏測試 | 封存庫 manifest（repo 之外） | 重寫一份隱藏測試 |
| 環境指紋 | `.harness/env-fingerprint.json` | 重跑機器/服務掃描 |

原本缺的是**進度檢查點**，現在補上：Orchestrator 在每個 task 狀態改變時
維護一個 `.harness/progress/<task_id>.md`（`.harness/` 本來就不進版控，
這條職責寫在 `.claude/agents/orchestrator.md` 的執行順序第 7 步）：

```markdown
# <task_id> 進度

- 狀態：實作中 / 待驗收 / 已驗收 / 阻塞
- 目前在哪一步：verifier-test-writer 已封存、implementer 進行中
- 權杖去向：已交回 Orchestrator（**不要把權杖本身寫進來**）
- 已完成：<條列，一行一件>
- 未完成：<條列>
- 已知決策：<為什麼選這個做法，避免下次重新推導>
- 下一步：<一句話，恢復時第一件要做的事>
```

這份檔案要小（幾百字元等級）。它的用途是**取代「重讀 repo 重建脈絡」**，
不是完整的工作紀錄——寫太長就失去意義了。

`.harness/progress/` 是 `.harness/` 底下唯一開放寫入的子目錄
（`guard-hidden-tests.py` 的 `HARNESS_PROGRESS_PREFIX`）；同一層的治理檔案
（鎖定清單、環境指紋、隱藏測試 manifest）依舊只能由對應腳本產生，
`.harness/progress/../locked-tests.list` 這種路徑戲法也擋得下來。

> ⚠️ 權杖絕對不能寫進檢查點。`.harness/` 不進版控，但 implementer 在同一台機器上，
> 而且 `guard-hidden-tests.py` 擋的是「存取」不是「別人寫進去的內容」。
> 這條跟 `verifier-test-writer.md` 的禁止事項是同一條。

### 3.3 每個 task 做完就 commit + push

跟上一條同一個道理，只是落在程式碼上：**未 commit 的工作在中斷時價值接近零**，
恢復時得重做。以 task 為單位 commit，讓一次中斷最多只損失一個 task 的進度，
而不是一整輪。

### 3.4 在 Pro 方案下，平行度是有害的

§4 會提到「平行度不省 token」——那是對 API 計費而言。
**在訂閱制底下，平行度是負面的**：

同時派三個子智能體，總 token 一樣多，但那些 token 全部集中在
**同一個時間視窗內**被消耗掉。也就是說平行度直接把消耗速率乘上三倍，
撞到上限的機率也跟著上升。而一旦撞上，三個 task 會一起停在半路，
每一個都要付一次恢復成本。

所以 `machine-profile.py` 給出的「這台機器可以同時跑幾個子智能體」是
**機器容量的上限，不是建議值**。Pro 方案下的實際建議：

- 序列執行，一個 task 做完（含驗收、commit）再開下一個
- 真的要平行，只平行**同一個 task 內互不相依**的部分，
  而且平行完立刻收斂，不要讓三條線同時往前跑
- 「反正機器跑得動」不是開平行的理由——瓶頸不在機器

### 3.5 讓重讀變便宜：不要動到前綴

被打斷後重開 session，內容會被重新讀進去。這件事有一個可以利用的性質：
**穩定不變的前綴內容比變動的內容便宜**（prompt caching 是靠前綴比對的，
從第一個變動的位元組開始，後面全部要重算）。

實務上的意思是：

- `CLAUDE.md` 與 agent 定義檔應該**穩定**。每次任務都去微調它們，
  等於每次都讓整個前綴失效——這是除了「乘數最高」之外，
  §2.4 那條規則的第二個理由
- 變動的東西（task-spec、程式碼、測試輸出）放後面，本來的載入順序就是這樣
- **不要在一個流程中途換模型**：快取是綁模型的，換模型等於整份重算。
  §2.2 的「先小後大」是**分階段**升級（低風險任務的第一輪驗收用小模型，
  出訊號才整輪改用大模型重驗），不是同一輪裡來回切換

### 3.6 額度是共用的：先確認要不要現在花

同一個訂閱底下，這個 repo 的任務跟你當天其他所有工作**共用同一份額度**。
所以有兩件事值得在開工前想一下：

- 這輪任務值不值得現在開？還是可以排在額度剛重置的時候
- `docs/improvement-suggestions.md` 這類 39,000 字元的歷史文件，
  在 Pro 方案下不只是「貴」，而是**直接把你推向上限**（見 §1 的警告）

## 4. 絕對不該省的地方

省 token 很容易滑坡成「把防線拆掉」。以下幾項省下來的錢，
換來的是整套機制失去意義：

| 不該省 | 為什麼 |
|---|---|
| 檢驗者與實作者分開 session | 共用上下文就等於自己驗自己，整個 SE-CoVe 前提消失 |
| 隱藏測試機制 | 它就是這個模板的核心價值 |
| 需求釐清的問答 | 省一輪問答，通常換來三輪失敗實作，更貴也更慢 |
| L3/L4 任務的重量模型 | 漏判一次的代價遠高於模型差價 |
| 回歸測試（188 案例） | 機制退化是無聲的，測試是唯一訊號 |

### 一個常見誤解：平行度不省 token

`machine-profile.py` 決定的「同時可派出幾個子智能體」是**時間**的最佳化，
不是 token 的。三個 task 平行跑跟序列跑，總 token 一樣多——
平行只是讓你早點知道結果。真要省 token，要從上面第 2 節下手。

而在訂閱制方案下更糟：總量一樣但**集中在同一個時間視窗**，平行度會直接
把消耗速率乘上倍數，讓你更快撞到上限（見 §3.4）。

## 5. 檢查清單

開始一輪任務前：

- [ ] task-spec 的「範圍邊界」有沒有填？（不填 = implementer 自己去找 = 最貴）
- [ ] 有沒有歧義該先問？（黃金法則第 7 條）
- [ ] 這輪的掃描結果能不能重用上一輪的？（同 session + 指紋相符）
- [ ] 這個 task 真的需要 L3/L4 嗎，還是 L2 就夠？
- [ ] 有沒有把 `improvement-suggestions.md` 這類歷史文件放進 agent 的閱讀路徑？

訂閱制（Pro）方案下額外要問（§3）：

- [ ] 這輪真的需要平行嗎？還是序列做完一個再開下一個就好？
- [ ] 上一個 task 有沒有 commit + push？（沒有的話中斷就得重做）
- [ ] `.harness/progress/<task_id>.md` 是不是反映目前的真實進度？
- [ ] 這輪有沒有必要改 `CLAUDE.md` 或 agent 定義檔？（改了等於讓前綴快取失效）

改動 `CLAUDE.md` 前：

- [ ] 這件事是不是每個 session 都必須知道？不是就放 `docs/`。
