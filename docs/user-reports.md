# 使用者回報的處理流程

> 這份文件講的是**別人跟你說「你的程式壞掉了」之後**要怎麼處理。
> 程式自己壞掉（測試紅、CI 掛）走 `docs/root-cause-and-fix.md`。

## 1. 為什麼這要獨立成一個入口

`root-cause-and-fix.md` 的五個觸發條件全是**機器產生的訊號**：驗收不通過、測試失敗、
CI 紅燈、防護誤擋、停損。它們有一個共同性質——**證據在事件發生的當下就完整存在了**：
錯誤輸出、exit code、平台版本、觸發指令，全都有。

使用者回報不是這樣。它是**人講的一句話**，而且通常是這句：「壞掉了。」

於是 RCA 的第一步（凍結證據）沒有東西可以凍結，第二步（穩定重現）在空氣中進行。
這中間缺的那一段，就是這份文件。

## 2. 誰負責

**Orchestrator。** 理由跟「只有它能寫記憶」「只有它能升版」是同一條：
它是唯一有全局視野、而且被允許跟使用者往返的角色。

- `implementer-*` 不該知道「這是誰回報的、他當時在做什麼」——它只依 task-spec 實作。
  讓它去猜回報者的意圖，等於讓它超出規格範圍發揮（黃金法則第 4 條）。
- `verifier-*` 不跟使用者互動。它驗的是「實作有沒有達成驗收標準」，
  而驗收標準是從回報**整理過之後**才產生的東西。

所以整個流程是：**使用者 ↔ Orchestrator**，往返到證據足夠為止，才輪到派工。

## 3. 第 0 步：先分流，不要直接當 bug 修

這一步放在最前面，因為**分流錯了，後面每一步都是錯的**。

一份回報有四種可能，而它們的去向完全不同：

| 類別 | 怎麼認 | 去向 |
|---|---|---|
| **真 bug** | 程式行為**與規格不符** | 走 §4 整理證據 → 開 bugfix task |
| **誤用** | 行為符合規格，使用者用錯了 | 回覆使用者。但要順便問自己：**他為什麼會這樣用？** |
| **規格如此但不符期待** | 行為符合規格，但規格本身不合理 | 這是**規格變更**，要使用者確認要不要改 |
| **新需求偽裝成 bug** | 「它不能做 X」，而 X 從來不在規格裡 | 這是新需求，走 `/task-plan` |

**判準只有一句：規格裡有沒有寫過這件事？** 沒寫過就不是 bug。

### 第四類最危險

「它不能匯出 PDF」聽起來完全像 bug，但如果規格從來沒有要求匯出 PDF，那它就是新需求。
**把新需求當 bug 修，就是在沒有經過拆解與估時的情況下擴大範圍**——違反黃金法則第 4 條，
而且它偏偏是四類裡最像 bug 的一個。

分不出來就回去問使用者：「你預期它做什麼？你是從哪裡知道它應該這樣做的？」
第二個問題特別有用——答案如果是「我以為」，那就不是 bug。

### 第二類不要只回一句「你用錯了」

誤用本身不是 bug，但**反覆出現的同一種誤用是文件或介面的問題**。
那是一個獨立的 task（改文件、改錯誤訊息、改預設值），不是這一次回報的修正範圍。
記下來交給 Orchestrator 判斷，不要順手一起改。

## 4. 第 1 步：把回報變成證據

分流結果是「真 bug」之後才做這一步。目標只有一個：**讓 RCA 步驟 2 有東西可以重現。**

用 `templates/issue-report-template.md` 收集。要問的東西跟**需求釐清完全不同**：

| | 需求釐清（新需求） | 故障釐清（回報） |
|---|---|---|
| 問什麼 | 目標、範圍邊界、驗收標準、語言/框架 | 版本、環境、操作步驟、預期 vs 實際、何時開始、以前正常嗎 |
| 為了什麼 | 讓 task 拆得出來 | 讓失敗**重現得出來** |

套需求釐清那套問法會問錯方向——問一個回報者「你的驗收標準是什麼」，
他只會覺得你在刁難。

### 最重要的一項是版本

沒有版本號，回報無法定位（不知道是哪一版壞的、也不知道他跑的是不是最新的），
修好之後也無法交代（不知道從哪一版起沒事）。

這就是為什麼模板產出的程式一定要有版本號，而且要讓人**不必跑工具就看得到**
（見 `docs/versioning.md`）。回報單上的版本欄位如果永遠是空的，
先去把那件事做好，不是繼續收沒有版本的回報。

### 重現不出來的時候

這是最常見的死路，處理原則有三條：

1. **不要猜著修。** RCA 步驟 2 已經寫死了：重現不了就不要往下走。
   在重現之前修的每一行都是猜測，而且會讓後續無法判斷「到底修好了沒」。
2. **但也不要就這樣掛著。** 把「重現不出來」本身當成待辦，問清楚**缺的是哪一項**
   再回去問，不要含糊地說「可以再多給一點資訊嗎」。
3. **問不到就明確結案成「無法重現」**，並告訴使用者需要什麼才能繼續。
   留一個假裝在處理的狀態，比說「目前重現不出來」更糟。

重現不出來最常見的三個原因，照這個順序查：

- **版本不同**（你在最新版上試，他跑的是三版之前的）
- **環境不同**（OS、locale、資料狀態、有沒有某個設定）
- **步驟裡有一個他覺得不重要所以沒講的動作**——這一個最常見，
  所以要問「你完整做了哪些步驟」，而不是「你做了什麼」

## 5. 第 2 步：轉成 task-spec

證據足夠之後，Orchestrator 開一個 **bug 修正 task**：

- **新的 task_id**，不要重開原本那個 task（重新封存會換權杖，也會把兩次驗收的
  嘗試次數混在一起，而那個計數是停損判斷的依據）
- task-spec 裡**註明這是 bug 修正**，並附上已定位的根因
- 回報單本身**不要整份塞進 task-spec**——它裡面有回報者的環境與敘述，
  對 implementer 是雜訊。只放「重現步驟 + 預期行為」。
- 之後 `verifier-test-writer` 依 `docs/root-cause-and-fix.md` §1.5 拆測試：
  **公開放被回報的那一個最小重現，隱藏放同一個根因的其他變體**，
  封存時加 `--kind bugfix`

修正發布出去時升 **PATCH**（`python3 scripts/version.py --bump patch`），
然後才有辦法回覆使用者「這個修正在 x.y.z 之後」。

### 追蹤記在哪

bug 修正開的是**新的 task_id**，所以「這個 bug 是從哪裡來的」如果沒有人寫下來，
線索就斷了——一個叫 `BUG-003` 的 task，光看名字說不出它在修什麼、為什麼存在。
三個地方各記一次，各有各的壽命：

| 記在哪 | 記什麼 | 活多久 |
|---|---|---|
| **回報單**（`templates/issue-report-template.md`） | 回報者環境、重現步驟、對應 task_id、**原始功能的 task_id** | 跟著回報走 |
| **驗收報告**（`reports/`） | 「任務來源」欄位：新需求／使用者回報＋回報單／bug 修正＋原 task_id | **進版控，最久** |
| **進度檢查點**（`.harness/progress/<task_id>.md`） | 「來源」一行 | 只到這次中斷結束——`.harness/` 不進版控 |

要長期回答「這個模組是不是一直出事」，看的是 `reports/`，不是檢查點。

## 6. 跟其他流程的銜接

```
使用者回報
   │
   ▼
[Orchestrator] 分流（§3）
   ├─ 誤用 → 回覆；反覆出現就另開文件/介面 task
   ├─ 規格如此 → 問使用者要不要改規格（規格變更，不是 bug）
   ├─ 新需求 → /task-plan
   └─ 真 bug
        │
        ▼
      整理證據（§4，templates/issue-report-template.md）
        │  重現不出來 → 問缺的那一項；問不到就結案成「無法重現」
        ▼
      開 bugfix task（§5）→ docs/root-cause-and-fix.md 的步驟 1–7
        │
        ▼
      驗收通過 → 升 PATCH → 回覆使用者「x.y.z 起修正」
        │
        ▼
      值得留給下次的判斷 → 寫記憶（docs/memory-management.md §3）
```

## 7. 刻意不做的事

**沒有對應的腳本。** 這份文件是規則層的，跟 `docs/memory-management.md` 一樣。

理由不是偷懶，是這裡沒有東西可以機械化：分流靠的是「規格裡有沒有寫過」，
而規格是自然語言；「重現步驟夠不夠」也沒有客觀判準——夠不夠的唯一測試就是
**真的去重現一次**，而那已經是 RCA 步驟 2 了。

硬做一個「回報單欄位檢查器」只會檢查到欄位非空，而一個填了「環境：我的電腦」
的回報單，欄位是滿的、資訊是零的。那種檢查會製造「已經檢查過了」的錯覺，
比沒有檢查更糟——這跟 `docs/versioning.md` §6 拒絕做版本雜湊稽核是同一個判斷：
**多一層換不到對應的價值時，就不要多那一層。**

真正有機械保證的是下游：`--kind bugfix` 讓「只修了被回報的那一個 case」
在驗收時就會被抓到（`root-cause-and-fix.md` §1.5），版本號讓「這個修正在哪一版」
是可查證的（`versioning.md`）。上游靠人問清楚，下游靠機制擋住——這樣分工是對的。
